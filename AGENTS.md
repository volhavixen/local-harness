# Универсальные инструкции local-harness

Эти правила задают рабочий процесс и требования к доказательствам. Модели, режим Plan/Default, рабочие папки и доступные инструменты определяются пользователем, проектом и фактическим окружением. Необязательный пример личных предпочтений находится в `examples/personal-preferences.md` репозитория; он не подключается автоматически и не является частью базовой установки.

## Режим работы

- Перед выполнением определить цель, разрешённые действия и критерии готовности; составить соразмерный задаче план. При порученной реализации довести работу через применимые проверки и исправления до проверяемого результата.
- Соблюдать согласованный режим работы и не выдавать текстовый план за переключение режима. Если необходимый режим недоступен, установить разрешённый дальнейший порядок до зависимого действия.
- Использовать модели и уровень рассуждений, заданные пользователем или окружением. Этот harness не требует конкретного семейства или версии модели и не меняет настройки приложения.
- Делегировать только в пределах действующих разрешений. Согласовывать ресурсы исполнителей; не считать наличие примера настроек разрешением на делегирование.

## Размещение проектов и материалов

- Использовать выбранный пользователем проект на его месте. Для нового проекта определить разрешённую рабочую папку; перед созданием материалов проверить фактический абсолютный путь с учётом symlink.
- Хранить существенное состояние и доказательства в согласованном постоянном каталоге вне репозитория. Фиксированное имя рабочей папки не требуется.
- Не переносить существующие папки и не изменять настройки размещения Codex без поручения. Установка skill не меняет `projectlessWorkspaceRoot`.

## Подключение local-harness

В начале задачи подключать `local-harness` из установленного каталога skills. Объём процедуры и проверки определять по самому skill и правилам проекта; подключение не означает запуск неприменимых этапов. Действующие пользовательские и проектные инструкции сохраняют приоритет.

Определять режим разработки или ревью и разрешённые действия. Публикация, push, merge, внешние сообщения и изменение CI требуют соответствующего поручения; уже данное разрешение сохраняется. Начало и возобновление — по [процедуре задачи](skills/local-harness/references/task.md).

## Окружение и инструкции любого проекта

Runtime, команды и версии определять по текущему проекту; не переносить настройки одного продукта или стека в другой автоматически.

- Перед работой читать доступные корневые и применимые вложенные `AGENTS.md`, руководство запуска и конфигурацию проверок. Если инструкций нет или они противоречат реальному проекту, сначала установить фактические команды и ограничения. При согласованной работе над harness восстановить краткие инструкции проекта с картой, запуском, обязательными проверками и правилами CI.
- Использовать объявленные проектом runtime, менеджер пакетов и lockfile. Проверять совместимость локального окружения с CI; устанавливать зависимости воспроизводимым способом без самовольного обновления lockfile и версий. Не навязывать всем проектам Node, pnpm или конкретный номер версии.
- В проекте по возможности иметь понятные команды диагностики окружения и быстрых проверок. Диагностика не должна печатать секреты. Агрегатор быстрых проверок должен запускать все независимые проверки даже после ошибки и возвращать ненулевой код при любой неудаче.
- Исключать генерируемые сборки, кэши и временные браузерные артефакты из проверок и Git, сохраняя проверку рабочих исходников. Использовать проектные точки расширения, не переписывать общий шаблон без необходимости.
- Для тестов и отдельных рабочих копий использовать отдельные порты, базы и каталоги сборки. Не останавливать чужие процессы и не сбрасывать рабочие данные. На ограниченной машине выполнять тяжёлые интеграционные и браузерные прогоны последовательно; число workers выбирать по ресурсам.

## Общая локальная очередь тяжёлых проверок

До тяжёлых проверок определить доступные ресурсы и согласованный способ взаимного исключения между чатами. Уже работающие процессы не прерывать. На Windows встроенная POSIX-очередь доступна через WSL; нативно использовать согласованный последовательный порядок и явно фиксировать отсутствие автоматической общей блокировки.

`tools/resource-queue/heavy_check.py` — необязательный инструмент для macOS/Linux/WSL. Следующие требования обязательны, если для окружения выбрана эта очередь. Перед запуском установить `HARNESS_QUEUE` в абсолютный путь единственного общего экземпляра helper; не устанавливать отдельные очереди для отдельных проектов. Если очередь не выбрана, соблюдать согласованную политику ресурсов; набор обязательных проверок не сокращается.

- Все новые ресурсоёмкие конечные команды (полные lint/типы, unit/integration, сборки, мутации, разрешённые браузерные/E2E-прогоны) запускать только через один общий helper: `python3 "$HARNESS_QUEUE" [параметры] -- <команда>`. Общая блокировка одна для согласованных участников в одной POSIX-среде, не на проект; запуски нативной Windows и других окружений автоматически не перехватываются. Не создавать отдельный `--state-dir`, не обходить очередь прямым запуском или фоновыми дочерними командами. При выбранной очереди этот helper обязателен независимо от использования helper записи `check.py`.
- Встроенный helper поддерживает 1 или 2 worker и по умолчанию использует 1. Для другой системы лимиты определять по проекту и ресурсам; этот технический предел helper не задаёт лимит всех проектов. Для Vitest/Jest использовать `--runner vitest` / `--runner jest`; для отдельно разрешённого Playwright — `--runner playwright`. Лимит задавать параметром очереди `--workers 1` или `--workers 2` перед разделителем `--`; helper сам добавляет флаг runner. Пример: `python3 "$HARNESS_QUEUE" --runner vitest --workers 1 -- pnpm exec vitest run`. Для другого стека сначала установить штатный способ ограничения; автоопределение по ядрам и неограниченный параллелизм запрещены. Для обычного pytest использовать последовательный запуск без xdist. Не менять runtime/менеджер пакетов проекта ради примера.
- Внутри занятого слота проверки выполнять последовательно: не использовать `&`, `Promise.all`, параллельный агрегатор или параллельные lint + typecheck + tests. Независимые проверки всё равно выполнить все, даже после ошибки; итоговый ненулевой код сохранить. Состав, полноту и обязательность проверок не ослаблять.
- Ожидание очереди означает «ожидает», а не PASS, skip или ошибку тестов. Проверить статус: `python3 "$HARNESS_QUEUE" --status`. Держать постоянный лог проверки штатным способом; очередь передаёт вывод и код завершения команды. Ожидая, продолжать чтение/анализ, без повторного запуска той же проверки.
- Новые обходы экранов, навигацию, reload и действия в браузере, которые могут вызвать dev-компиляцию, согласовывать с тяжёлыми тестами через тот же слот. До начала выполнить `python3 "$HARNESS_QUEUE" --reserve-screens <метка-чата-и-задачи>` как продолжающийся процесс и дождаться JSON-события `screens_acquired` с личным `token`. До этого события не открывать/обновлять экраны и не запускать отдельный прогрев. Пока свой screen-слот занят, пройти нужный конечный сценарий через браузерные инструменты, дождаться загрузки, ответов и завершения вызванной компиляции по логам сервера. Затем обязательно освободить свою бронь: `python3 "$HARNESS_QUEUE" --release <свой-token>` и дождаться завершения процесса брони. При ошибке сценария тоже завершить/дождаться вызванной компиляции и освободить бронь. Не запускать тесты внутри своей брони: это взаимная блокировка; сначала release, затем отдельная команда через очередь.
- Screen-бронь и тесты взаимно исключают друг друга во всех чатах. Не освобождать чужой token и не вводить автоматический таймаут, который отпустит слот посреди компиляции. Статус показывает метку, token и владельца; забытая бронь требует проверки владельцем, а не удаления lock-файла. Долгоживущий dev-сервер остаётся запущенным вне очереди; слот удерживается только на время конечного браузерного обхода/компиляции, не на всё время жизни сервера, watcher или браузера. Известные новые прогревы и повторные компиляции тоже относятся к этой броне. Не запускать несколько новых тяжёлых серверов одновременно; использовать согласованный работающий экземпляр, когда это уместно. Уже начатый обход и компиляцию не прерывать — применять порядок со следующего сценария. Не завершать чужие процессы. Отмена ожидающей команды не должна затрагивать владельца слота.
- Это локальное ограничение ресурсов. CI, репозитории, обязательные проверки и ограничения на запуск E2E остаются по действующим указаниям пользователя. Чтение кода, поиск и анализ можно выполнять параллельно. Руководство: `README.md` рядом с выбранным helper (в репозитории — `tools/resource-queue/README.md`).

## Уборка собственных временных браузеров и серверов

- При создании временного dev-сервера, браузерного профиля/сеанса или другого фонового процесса записывать владельца (чат/задача), назначение, PID с временем запуска, рабочий каталог, порт и способ штатного завершения. Для браузера сохранять ID созданного сеанса/вкладок. Запись хранить в состоянии своей задачи; не считать любой старый процесс своим по имени или возрасту.
- После завершения задачи или ненужной более проверки закрывать только созданные этим чатом временные браузерные сеансы/вкладки и штатно завершать собственные временные серверы, если они больше никому не нужны. Перед завершением сверять PID и время запуска, владение, текущую команду и отсутствие работающих проверок/компиляции и согласованного использования другим чатом. При неоднозначности оставить процесс и явно описать ограничение. Текущую работу не прерывать: правило применяется по окончании использования, без ретроспективной массовой остановки.
- Использовать штатные API закрытия своего браузерного сеанса и мягкое завершение только своего процесса/группы. Не применять `killall`, `pkill node/chrome`, закрытие всех окон браузера, остановку общего Docker или сервера другого чата. Пользовательские браузеры и ранее существовавшие серверы не принадлежат чату только потому, что он ими воспользовался.
- Перед уборкой дождаться ответов и завершения начатой компиляции, освободить свою screen-бронь, если очередь подключена, и закрыть свои временные сеансы. Не оставлять забытые брони. Если сервер нужен для ручной приёмки пользователя или передан другому чату, сохранить его работающим и записать назначение, URL, нового ответственного и условие будущего завершения; не объявлять такой процесс убранным.
- После уборки проверить, что собственный процесс/сеанс завершился, а согласованные общие ресурсы сохранились. В итоговом отчёте кратко отметить убранные ресурсы и оставленные для приёмки/совместной работы. Проекты, базы, Docker volumes, результаты проверок и постоянные логи эта уборка не удаляет. Не вводить таймер автоматического убийства процессов.

## Тесты, браузерные прогоны и CI для любого проекта

- Обязательные unit/integration и применимые быстрые проверки (форматирование, lint, типы или их аналоги в стеке проекта) должны проходить. Проверка только изменённых файлов — дополнительная обратная связь, она не заменяет установленный обязательный полный набор.
- Изменённый пользовательский путь проверять целевым браузерным прогоном для веб-продукта, а для другого типа приложения — соответствующей проверкой взаимодействия. Пустой выбор тестов не доказывает готовность. Для документации и инфраструктуры выбирать проверки по затронутому поведению, не запускать несвязанные UI-сценарии формально.
- Условия запуска локального и полного E2E, а также блокирующий статус CI определяются проектом и явными указаниями пользователя. Не запускать запрещённые проверки и не менять CI без поручения. Для разрешённых целевых проверок сохранять требования к фактическому покрытию; незапуск отражать честно.
- При настройке CI обязательные быстрые проверки и unit/integration должны блокировать интеграцию и выпуск. Независимые проверки разделять, чтобы ошибка одной не скрывала остальные. Сборки, ведущие к выпуску, должны ждать обязательных проверок, а не ручного полного E2E. Не менять CI другого проекта только из-за чтения этих инструкций: применять правила в пределах согласованной задачи.
- Skips, `fixme`, отменённые и незапущенные jobs не считать PASS. В отчёте отдельно указывать passed, failed, skipped и непроверенное. Отсутствующие внешние сервисы или переменные для отдельных проверок прямо называть ограничением.
- Отделять ошибки приложения/тестов от сбоев инфраструктуры, сети и runners. `stuck_pending_no_matching_runners` без назначенного runner и времени старта означает отсутствие выполнения. Не объяснять такой сбой бездействием пользователя.
- Агент отвечает за диагностику и доказательный отчёт: команда, рабочая версия, код завершения, фактический результат и ограничения. Локальные проверки, локальные контейнеры, серверная валидация конфигурации и реальные CI jobs — разные доказательства; не подменять одно другим.
- Не подделывать цвета статусов CI, не скрывать ошибки ослаблением тестов и не увеличивать таймауты без установленной причины. Не выдавать неподтверждённый результат за готовый.


## Обязательный порядок при расширении существующего продукта

Если задача касается расширения или изменения имеющегося функционала веб-приложения, сначала ОБЯЗАТЕЛЬНО проверить его в работающем приложении по предоставленному пользователем URL, включая localhost: пройти связанные сценарии, выяснить, что уже реализовано, и точно снять существующий дизайн. Сохранить скриншоты экранов, модальных окон, состояний и адаптива; сверить компоненты, размеры, отступы, шрифты, иконки и токены с исходниками. Затем расширять существующие компоненты и UX-паттерны, а не изобретать их заново. До показа результата самостоятельно проверить весь изменённый путь и сравнить его с исходным приложением: пользователь не должен отслеживать придуманные замены и регрессии. Если приложение недоступно, назвать конкретную причину и предел проверки, не выдавая предположения за проверенное поведение.

Для CLI, desktop и mobile до изменения пройти связанный исходный рабочий сценарий
подходящим способом взаимодействия. Для desktop/mobile с пользовательским
интерфейсом также применять требования первого абзаца к исходному и итоговому
проходу, фиксации дизайна, скриншотам, сверке с исходниками и сохранению компонентов
и UX-паттернов; вместо URL использовать подходящий способ запуска.
Автономную библиотеку или машинный API без
пользовательского приложения проверять через соответствующий вызов, пример или
тест; несвязанный UI-сценарий не запускать. Вид проверки выбирать по затронутому
объекту и [матрице применимости](skills/local-harness/references/scope-and-applicability.md).
Недоступность нужного приложения или среды фиксировать как конкретное ограничение,
сохраняя критерии готовности из матрицы.

## Понимание задач и эффективность работы

- Во время работы и перед сдачей сопоставляй намерение пользователя с фактическим результатом: «ожидалось → получено → расхождение → причина → исправление → проверка». Основание — запрос, согласованные критерии и наблюдаемые факты. При обнаруженном расхождении исправляй подтверждённую причину в пределах задачи и проверяй результат. Для существенной работы сохраняй этот разбор в существующем состоянии задачи. Запись правила сама по себе не доказывает исправление поведения.
- При существенном исправлении пользователя сначала проверь, покрывает ли требование существующее правило. Различай: правило не попало в контекст, сформулировано неоднозначно, конфликтует с другим источником либо было доступно и не выполнено. Причину устанавливай по фактам; неизвестную оставляй неизвестной. Исправляй подтверждённую причину: маршрут чтения, формулировку, конфликт или проверку исполнения. Новое постоянное правило добавляй только при отсутствии подходящего существующего, в минимально подтверждённой области применения и в пределах разрешённых правок. Частный случай не обобщай на все проекты.
- Для чтения и поиска сначала используй точный путь из доступных инструкций или каталога skills, затем ближайший подходящий каталог. Расширяй область по конкретному пробелу в результатах. Для списка правил просматривай каталог правил; для истории задачи — выбранный run-каталог. При обрезанном выводе сузь запрос и перечитай нужный фрагмент.
- Объяснять результат с учётом знаний пользователя; помогать формулировать требования и самостоятельно решать технические вопросы в согласованном объёме.
- Сначала выясняй доступные факты. Затем небольшими порциями уточняй цель, ожидаемое поведение, ограничения и критерии готовности до ясного понимания задачи. Предлагай понятные варианты с рекомендацией; существенные пробелы не заполняй догадками.
