# Постоянные пользовательские инструкции

## Режим работы и выбор моделей

- По умолчанию использовать agentic workflow: план → выполнение согласованной задачи → применимые проверки → исправление подтверждённых ошибок → повторная проверка затронутого до готового результата. Если поручена реализация, не завершать работу одним планом. Этот порядок не отменяет обязательные проверки, ограничения и необходимые разрешения.
- Планирование обязательно в начале каждой новой задачи без напоминания пользователя: до реализации составить краткий план, соразмерный задаче. Режим `/plan` использовать, когда он доступен; отсутствие автоматического переключения этого режима не освобождает от планирования. Явное указание пользователя работать иначе имеет приоритет.
- Перед началом новой задачи проверять фактически переданный режим работы. Считать Plan включённым только при явном указании `Collaboration Mode: Plan` в системном контексте. Составление плана текстом не считать включением режима. Если требуется Plan, но фактически передан Default, сразу сообщить о расхождении и не переходить к реализации до настоящего переключения либо прямого разрешения пользователя работать в Default.
- Старшая модель для планирования и координации — Sol 6.1 с уровнем рассуждения High (`gpt-6.1-sol`, `high`).
- Для исполнителей выбирать более младшие доступные модели. Параллельное делегирование независимых подзадач разрешено пользователем без отдельного подтверждения; количество исполнителей выбирать по пользе задачи и фактическим лимитам платформы. Тяжёлые локальные проверки всех исполнителей остаются в одной общей очереди.
- Модели версии 6.2 и модели семейства Astra 6 не запускать без прямого требования пользователя; не выбирать их автоматически для основной работы, исполнителей или замены недоступной модели.
- При запуске skill не добавлять уведомление о невозможности переключить основную модель, включая фразу «Переключить основную модель средствами этого чата я не могу» и её перефразирования. Ограничение переключения сообщать при прямом запросе пользователя на переключение или если оно препятствует выполнению задачи; не выдавать запись предпочтения за фактическое переключение.

## Обязательное размещение проектов без выбранного проекта

- Если пользователь не выбрал существующий проект, создавать новый проект и его рабочую папку ТОЛЬКО внутри `~/Documents/Work`. Это общее правило для всех проектов и чатов Codex.
- Перед созданием проекта, рабочих файлов, результатов или временных материалов проверить фактический абсолютный путь с учётом символических ссылок: он должен находиться внутри `~/Documents/Work/`. Использовать отдельную подпапку задачи; не создавать проект непосредственно в `Documents`, `Documents/Codex`, домашней папке или другом месте за пределами `Work`.
- Автоматически назначенная Codex папка за пределами `Work` не является разрешением работать в ней. До создания файлов выбрать рабочую подпапку внутри `Work` и выполнять работу там. Если переназначить папку средствами приложения нельзя, прямо сообщить об ограничении; не продолжать создавать материалы проекта снаружи.
- Для чатов без проекта сохранять настройку `[desktop].projectlessWorkspaceRoot = "~/Documents/Work"`. Не менять её на другой путь без прямого указания пользователя.
- Существующие явно выбранные проекты использовать по их фактическому расположению. Перенос уже существующих папок выполнять только по отдельному поручению пользователя. Служебные данные самого Codex в `~/.codex` не являются папкой нового проекта.

## Личный harness Codex

Личный skill `local-harness` подключать всегда автоматически при начале задачи,
без напоминания или отдельного вызова со стороны пользователя:
`~/.codex/skills/local-harness/SKILL.md`.
Объём процедуры и применимость проверок определять по правилам самого skill;
автоматическое подключение не означает запуск неприменимых этапов.

Определять режим разработки или ревью и порученные действия. Обычно коллега
проводит ревью MR и merge в main; личная подготовка не подразумевает публикацию,
push, merge или изменение общего CI. Явные разрешения пользователя сохраняются.
Начало, хранение состояния и возобновление — по
[процедуре задачи](skills/local-harness/references/task.md);
условные процедуры читать только при их применимости.

## Окружение и инструкции любого проекта

Эти правила — общие предпочтения пользователя для всех проектов в Codex, независимо от языка, фреймворка, ОС и поставщика CI. Конкретные команды и версии определять по проекту; не переносить настройки CRM или JavaScript в другие проекты автоматически.

- Перед работой читать доступные корневые и применимые вложенные `AGENTS.md`, руководство запуска и конфигурацию проверок. Если инструкций нет или они противоречат реальному проекту, сначала установить фактические команды и ограничения. При согласованной работе над harness восстановить краткие инструкции проекта с картой, запуском, обязательными проверками и правилами CI.
- Использовать объявленные проектом runtime, менеджер пакетов и lockfile. Проверять совместимость локального окружения с CI; устанавливать зависимости воспроизводимым способом без самовольного обновления lockfile и версий. Не навязывать всем проектам Node, pnpm или конкретный номер версии.
- В проекте по возможности иметь понятные команды диагностики окружения и быстрых проверок. Диагностика не должна печатать секреты. Агрегатор быстрых проверок должен запускать все независимые проверки даже после ошибки и возвращать ненулевой код при любой неудаче.
- Исключать генерируемые сборки, кэши и временные браузерные артефакты из проверок и Git, сохраняя проверку рабочих исходников. Использовать проектные точки расширения, не переписывать общий шаблон без необходимости.
- Для тестов и отдельных рабочих копий использовать отдельные порты, базы и каталоги сборки. Не останавливать чужие процессы и не сбрасывать рабочие данные. На ограниченной машине выполнять тяжёлые интеграционные и браузерные прогоны последовательно; число workers выбирать по ресурсам.

## Общая локальная очередь тяжёлых проверок

Правило пользователя от 20 ноября 2026 года действует для всех проектов, рабочих копий и чатов на этом компьютере. Уже запущенные проверки не прерывать и не перенастраивать на ходу.

- Все новые ресурсоёмкие конечные команды (полные lint/типы, unit/integration, сборки, мутации, разрешённые браузерные/E2E-прогоны) запускать только через один общий helper: `python3 ~/Documents/Work/CodexTools/resource-queue/heavy_check.py [параметры] -- <команда>`. Общая блокировка одна на компьютер, не на проект. Не создавать отдельный `--state-dir`, не обходить очередь прямым запуском или фоновыми дочерними командами. Этот helper обязателен для очереди, даже если helper записи доказательств `check.py` не используется.
- По умолчанию тесты используют 1 worker; максимум 2, только при нормальном давлении на память и наличии свободных ресурсов. Для Vitest/Jest использовать `--runner vitest` / `--runner jest`; для отдельно разрешённого Playwright — `--runner playwright`. Лимит задавать параметром очереди `--workers 1` или `--workers 2` перед разделителем `--`; helper сам добавляет флаг runner. Пример: `python3 ~/Documents/Work/CodexTools/resource-queue/heavy_check.py --runner vitest --workers 1 -- pnpm exec vitest run`. Для другого стека сначала установить штатный способ ограничения; автоопределение по ядрам и неограниченный параллелизм запрещены. Для обычного pytest использовать последовательный запуск без xdist. Не менять runtime/менеджер пакетов проекта ради примера.
- Внутри занятого слота проверки выполнять последовательно: не использовать `&`, `Promise.all`, параллельный агрегатор или параллельные lint + typecheck + tests. Независимые проверки всё равно выполнить все, даже после ошибки; итоговый ненулевой код сохранить. Состав, полноту и обязательность проверок не ослаблять.
- Ожидание очереди означает «ожидает», а не PASS, skip или ошибку тестов. Проверить статус: `python3 ~/Documents/Work/CodexTools/resource-queue/heavy_check.py --status`. Держать постоянный лог проверки штатным способом; очередь передаёт вывод и код завершения команды. Ожидая, продолжать чтение/анализ, без повторного запуска той же проверки.
- Новые обходы экранов, навигацию, reload и действия в браузере, которые могут вызвать dev-компиляцию, согласовывать с тяжёлыми тестами через тот же слот. До начала выполнить `python3 ~/Documents/Work/CodexTools/resource-queue/heavy_check.py --reserve-screens <метка-чата-и-задачи>` как продолжающийся процесс и дождаться JSON-события `screens_acquired` с личным `token`. До этого события не открывать/обновлять экраны и не запускать отдельный прогрев. Пока свой screen-слот занят, пройти нужный конечный сценарий через браузерные инструменты, дождаться загрузки, ответов и завершения вызванной компиляции по логам сервера. Затем обязательно освободить свою бронь: `python3 ~/Documents/Work/CodexTools/resource-queue/heavy_check.py --release <свой-token>` и дождаться завершения процесса брони. При ошибке сценария тоже завершить/дождаться вызванной компиляции и освободить бронь. Не запускать тесты внутри своей брони: это взаимная блокировка; сначала release, затем отдельная команда через очередь.
- Screen-бронь и тесты взаимно исключают друг друга во всех чатах. Не освобождать чужой token и не вводить автоматический таймаут, который отпустит слот посреди компиляции. Статус показывает метку, token и владельца; забытая бронь требует проверки владельцем, а не удаления lock-файла. Долгоживущий dev-сервер остаётся запущенным вне очереди; слот удерживается только на время конечного браузерного обхода/компиляции, не на всё время жизни сервера, watcher или браузера. Известные новые прогревы и повторные компиляции тоже относятся к этой броне. Не запускать несколько новых тяжёлых серверов одновременно; использовать согласованный работающий экземпляр, когда это уместно. Уже начатый обход и компиляцию не прерывать — применять порядок со следующего сценария. Не завершать чужие процессы. Отмена ожидающей команды не должна затрагивать владельца слота.
- Это локальное ограничение ресурсов. CI, репозитории, обязательные проверки и ограничения на запуск E2E остаются по действующим указаниям пользователя. Чтение кода, поиск и анализ можно выполнять параллельно. Руководство: `~/Documents/Work/CodexTools/resource-queue/README.md`.

## Уборка собственных временных браузеров и серверов

- При создании временного dev-сервера, браузерного профиля/сеанса или другого фонового процесса записывать владельца (чат/задача), назначение, PID с временем запуска, рабочий каталог, порт и способ штатного завершения. Для браузера сохранять ID созданного сеанса/вкладок. Запись хранить в состоянии своей задачи; не считать любой старый процесс своим по имени или возрасту.
- После завершения задачи или ненужной более проверки закрывать только созданные этим чатом временные браузерные сеансы/вкладки и штатно завершать собственные временные серверы, если они больше никому не нужны. Перед завершением сверять PID и время запуска, владение, текущую команду и отсутствие работающих проверок/компиляции и согласованного использования другим чатом. При неоднозначности оставить процесс и явно описать ограничение. Текущую работу не прерывать: правило применяется по окончании использования, без ретроспективной массовой остановки.
- Использовать штатные API закрытия своего браузерного сеанса и мягкое завершение только своего процесса/группы. Не применять `killall`, `pkill node/chrome`, закрытие всех окон браузера, остановку общего Docker или сервера другого чата. Пользовательские браузеры и ранее существовавшие серверы не принадлежат чату только потому, что он ими воспользовался.
- Перед уборкой дождаться ответов и завершения начатой компиляции, освободить свою screen-бронь в общей очереди и закрыть свои временные сеансы. Не оставлять забытые брони. Если сервер нужен для ручной приёмки пользователя или передан другому чату, сохранить его работающим и записать назначение, URL, нового ответственного и условие будущего завершения; не объявлять такой процесс убранным.
- После уборки проверить, что собственный процесс/сеанс завершился, а согласованные общие ресурсы сохранились. В итоговом отчёте кратко отметить убранные ресурсы и оставленные для приёмки/совместной работы. Проекты, базы, Docker volumes, результаты проверок и постоянные логи эта уборка не удаляет. Не вводить таймер автоматического убийства процессов.

## Тесты, браузерные прогоны и CI для любого проекта

- Обязательные unit/integration и применимые быстрые проверки (форматирование, lint, типы или их аналоги в стеке проекта) должны проходить. Проверка только изменённых файлов — дополнительная обратная связь, она не заменяет установленный обязательный полный набор.
- Изменённый пользовательский путь проверять целевым браузерным прогоном для веб-продукта, а для другого типа приложения — соответствующей проверкой взаимодействия. Пустой выбор тестов не доказывает готовность. Для документации и инфраструктуры выбирать проверки по затронутому поведению, не запускать несвязанные UI-сценарии формально.
- Долгий полный E2E — ручной и неблокирующий, не на каждый push или MR/PR. В CI выражать это штатными настройками используемой платформы (например, `when: manual` и `allow_failure: true` в GitLab). Целевые прогоны для изменённого пути остаются обязательными.
- При настройке CI обязательные быстрые проверки и unit/integration должны блокировать интеграцию и выпуск. Независимые проверки разделять, чтобы ошибка одной не скрывала остальные. Сборки, ведущие к выпуску, должны ждать обязательных проверок, а не ручного полного E2E. Не менять CI другого проекта только из-за чтения этих инструкций: применять правила в пределах согласованной задачи.
- Skips, `fixme`, отменённые и незапущенные jobs не считать PASS. В отчёте отдельно указывать passed, failed, skipped и непроверенное. Отсутствующие внешние сервисы или переменные для отдельных проверок прямо называть ограничением.
- Отделять ошибки приложения/тестов от сбоев инфраструктуры, сети и runners. `stuck_pending_no_matching_runners` без назначенного runner и времени старта означает отсутствие выполнения. Не объяснять такой сбой бездействием пользователя.
- Агент отвечает за диагностику и доказательный отчёт: команда, рабочая версия, код завершения, фактический результат и ограничения. Локальные проверки, локальные контейнеры, серверная валидация конфигурации и реальные CI jobs — разные доказательства; не подменять одно другим.
- Не подделывать цвета статусов CI, не скрывать ошибки ослаблением тестов и не увеличивать таймауты без установленной причины. Пожелание жёлтого E2E означает неблокирующую job. Не выдавать неподтверждённый результат за готовый.


## Обязательный порядок при расширении существующего продукта

Если задача касается расширения или изменения имеющегося функционала веб-приложения, сначала ОБЯЗАТЕЛЬНО проверить его в работающем приложении по предоставленному пользователем URL, включая localhost: пройти связанные сценарии, выяснить, что уже реализовано, и точно снять существующий дизайн. Сохранить скриншоты экранов, модальных окон, состояний и адаптива; сверить компоненты, размеры, отступы, шрифты, иконки и токены с исходниками. Затем расширять существующие компоненты и UX-паттерны, а не изобретать их заново. До показа результата самостоятельно проверить весь изменённый путь и сравнить его с исходным приложением: пользователь не должен отслеживать придуманные замены и регрессии. Если приложение недоступно, назвать конкретную причину и предел проверки, не выдавая предположения за проверенное поведение.

Для CLI, desktop и mobile до изменения пройти связанный исходный рабочий сценарий
подходящим способом взаимодействия. Для desktop/mobile с пользовательским
интерфейсом также применять требования первого абзаца к исходному и итоговому
проходу, фиксации дизайна, скриншотам, сверке с исходниками и сохранению компонентов
и UX-паттернов; вместо URL использовать подходящий способ запуска.
Автономную библиотеку или машинный API без
пользовательского приложения проверять через соответствующий вызов, пример или
тест; несвязанный UI-сценарий не запускать. Вид проверки выбирать по затронутому
объекту и [матрице применимости](skills/local-harness/references/scope-and-applicability.md).
Недоступность нужного приложения или среды фиксировать как конкретное ограничение,
сохраняя критерии готовности из матрицы.

## Понимание задач и эффективность работы

- Во время работы и перед сдачей сопоставляй намерение пользователя с фактическим результатом: «ожидалось → получено → расхождение → причина → исправление → проверка». Основание — запрос, согласованные критерии и наблюдаемые факты. При обнаруженном расхождении исправляй подтверждённую причину в пределах задачи и проверяй результат. Для существенной работы сохраняй этот разбор в существующем состоянии задачи. Запись правила сама по себе не доказывает исправление поведения.
- При существенном исправлении пользователя сначала проверь, покрывает ли требование существующее правило.
