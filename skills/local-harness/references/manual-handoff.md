# Ручная приёмка

Этот раздел описывает передачу среды пользователю, отдельно от T6 агента.
Передавать приложение, если задача требует пользовательской проверки, а не для
формального завершения документации/инфраструктуры. Порядок самостоятельного T6 и его отличие от пользовательской приёмки — в
[процедуре T6](testing-stages.md#6-самостоятельная-ручная-проверка--перед-показом-пользователю);
применимость и ограничения — в [матрице](scope-and-applicability.md).
До проверки URL или показа среды соблюдать
[общую очередь и screen-бронь](run-results.md#обязательная-очередь-тяжёлых-локальных-проверок).

Тестовый runner обычно останавливает свой сервер: при необходимости подготовить
отдельный сервер для пользователя. Перед передачей проверить URL и health, указать
версию, время проверки, владельца процесса и срок жизни среды. Позднее доступность
не гарантировать без новой проверки. При отсутствии доступа назвать причину.

В `manual-checklist.md` записать: версия, URL, роли и подготовленные тестовые данные;
затем 5–10 строк «роль/подготовка → действие → ожидаемый результат». Для маленького
пути достаточно меньшего числа. Доступы выдавать безопасно для изолированных
искусственных аккаунтов; реальные пароли не включать в общий отчёт/skill.

Показать уровень свидетельства по существенным требованиям:

| Свидетельство | Предел |
| --- | --- |
| Просмотр кода теста | Описывает проверку, но не подтверждает её выполнение |
| Unit | Подтверждает правило в изоляции, не реальный HTTP-маршрут или UI |
| Integration/API через реальный маршрут | Подтверждает взаимодействие/ответ, не нажатие кнопки и не отдельный unit-этап |
| Автоматизированный UI | Подтверждает конкретное взаимодействие и состояние, не самостоятельный ручной проход T6 |
| Собственный ручной проход | Подтверждает лично выполненные сценарии T6, не заменяет применимый T5 |
| Прямой вызов job | Не доказывает работу scheduler |
| Double/фикстура почты | Не доказывает реальную IMAP/SMTP-доставку |
| Сдвиг на неделю | Не доказывает точную границу четырёх рабочих часов |

При сравнении UI сохранить состояния до/после при одинаковых данных, ролях и
viewport; старый дефект отделить от внесённого изменением. В отчёте указать
скриншоты и границы проверки, включая адаптив/внешние сервисы, если не проверены.
Handoff может честно завершиться «найдены блокеры»: завершение отчёта ревью
не означает готовности MR/продукта. Результаты оформить по
[форме handoff](../assets/handoff.md) и [критерию готовности](scope-and-applicability.md#3-применимость-отдельно-от-результата);
сами findings не отменяют доступные применимые проверки.
