# Постоянные результаты

Результаты хранятся вне проекта в каталоге текущей задачи. Для каждой попытки —
отдельный ID; повтор не перезаписывает прежнюю. Минимум: cwd, head/идентичность,
команда без секретов, источник, время, status, exit code, log и фактическое покрытие.
Для dirty-копии сохранить список относящихся к задаче файлов и их хеши. Игнорируемые
env и секреты не читать ради fingerprint. Для негитового проекта задать версию
в task.md; отсутствие Git не повод менять стек.

## Очередь тяжёлых локальных проверок

До тяжёлой команды или нового браузерного сценария обязательно прочитать и
соблюдать [полную политику общей очереди и screen-брони](../../../AGENTS.md#общая-локальная-очередь-тяжёлых-проверок).
Это источник выбора политики ресурсов и, если очередь подключена, порядка запуска, workers, ожидания и освобождения слота. Отсутствие очереди не разрешает пропуск проверок.

При внешней обёртке очередью `check.py` ещё не вызван до получения слота:
отсутствие его `result.json` в это время не повод повторять команду.

## Необязательный helper записи доказательств

Использовать доступный Python 3.9+ для личного инструмента, независимо от runtime
приложения. Команда после `--` выполняется без shell и получает обычное окружение.
Для конвейеров/перенаправлений предпочесть штатный script проекта; оболочку
запускать явно только когда нужна, с корректным quoting.

Пример для macOS/Linux/WSL с заранее настроенной переменной `HARNESS_QUEUE`:

```sh
python3 "$HARNESS_QUEUE" \
  --runner pytest --workers 1 -- \
  python3 ~/.codex/skills/local-harness/scripts/check.py \
  --run /absolute/evidence-directory/example-run --name unit-01 \
  --cwd /absolute/project-directory -- python3 -m pytest
```

Пример не означает, что всем проектам нужен pytest: вместо него использовать
проверенную команду текущего проекта. Штатный pnpm с Corepack, uv, Go, cargo и т. п.
определяются проектом. При отказе от helper записи выполнить ту же запись
обычными инструментами.

Helper создаёт `checks/unit-01/result.json` и `output.log`. JSON записывается
атомарно до запуска, при старте дочернего процесса и после завершения. Лог пишет
сама команда; для немедленных строк может требоваться её штатный unbuffered-режим.
Файлы приватны на POSIX (0600, каталоги 0700); Windows ACL этим не гарантируются.
Чувствительные аргументы будут сохранены: не передавать секреты в argv.
Окружение целиком не сохраняется. Лог может содержать вывод приложения с секретами:
автоматического надёжного redaction нет; перед передачей проверить и очистить копию.

## Интерпретация JSON

- `status=passed` у helper означает **только exit 0 процесса**. Покрытие независимо
  в `coverage.status=not_assessed` и остаётся непроверенным до чтения runner reports.
- `failed` — ненулевой код, не автоматический диагноз теста/инфраструктуры.
  `blocked` + `launch_error` — программу не удалось запустить; тесты не выполнялись.
- SIGINT/SIGTERM даёт `interrupted`; helper останавливает только собственную
  дочернюю группу. SIGKILL, закрытие компьютера или потеря сессии могут оставить
  `running`. Это отсутствие подтверждённого итога, а не PASS. Чужие PID не убивать.
- `counts` остаются `null`, пока их не подтвердил отчёт runner. `null` не равно 0.
- Head и состояние tracked-файлов фиксируются до и после. `revision_changed=true`
  или `tracked_content_changed=true` означает изменение исходников во время прогона;
  такой прогон не подтверждает готовность одной стабильной версии.
  `tracked_diff_sha256` не включает
  содержимое untracked/ignored файлов: дополнить идентичность по релевантным файлам.

Runner JSON/JUnit/trace направлять в уникальный каталог попытки. Если runner пишет
в общий путь, скопировать отчёт в `checks/<attempt-id>/artifacts/` и записать SHA-256
до следующего запуска. В оценке указывать сохранённую копию, а не перезаписываемый
исходник. Если файл уже заменён, не восстанавливать старые результаты по новому файлу:
оставить прежнее покрытие непроверенным и отметить утраченное доказательство.

После чтения сохранённого отчёта дополнить запись или сохранить отдельное `assessment.json`
с `coverage.status` (`verified`, `incomplete`, `not_assessed`), ожидаемыми test IDs,
фактически исполненными IDs/статусами, причиной ограничения и ссылкой на отчёт.
Не менять реальные коды завершения и исходные счётчики.

## Выборка и доказательства

До целевого прогона записать ожидаемые specs/tests и setup-зависимости. `--list`
подтверждает collection, но не выполнение. После сверить отчёт: нулевой выбор,
skipped/time=0 и блокировка зависимостью оставляют целевой путь непроверенным.
Использовать штатный изолированный режим проекта, если предусмотрен; не чинить
чужой граф тестов ради личного запуска. Test count setup не выдавать за count specs.

Сохранять счётчики trace/JUnit отдельно с их форматом: некоторые runners по-разному
учитывают errors, skipped и did_not_run. Не складывать два представления одного
запуска. Две skipped проверки БД — ограничение, даже при exit 0 остального набора.

Источники различать явно: `local`, `local_container`, `ci_lint`, `ci_job`, `manual`.
Для CI добавить job/pipeline URL и SHA; status pipeline не заменяет job/test report.
Для отрицательных проверок применять
[проверку причины отказа](edge-cases.md#4-проверять-там-где-может-произойти-нарушение),
для периодических — [проверку временных границ](edge-cases.md#3-выбрать-опасные-сочетания-а-не-только-отдельные-признаки).

## Нестабильные прогоны и диагностические повторы

При нестабильном прогоне сохранять первоначальный сбой, входные данные и среду,
назначение и результаты диагностических повторов. Различать дефект продукта,
гонку или изоляцию теста и сбой окружения; неизвестную причину оставлять неизвестной.
Поздний успешный повтор не стирает исходный сбой и не доказывает устранение причины.
Необъяснённые причины и влияние на гарантии отражать как ограничения готовности.

Увеличение retries или перевод обязательной проверки в skip не устраняют пробел
гарантии. Временные исключения оформлять по действующей политике проекта с
ответственным и условием возврата. Трактовка фактических статусов сохраняется по
[интерпретации JSON](#интерпретация-json); итоговая оценка — по
[критерию готовности](scope-and-applicability.md#3-применимость-отдельно-от-результата).

## Повторное использование и утраченный итог

После исправления найденной ошибки повторить затронутые проверки и обязательные
проверки проекта на итоговой версии. Не повторять несвязанные тяжёлые прогоны
без основания. Для остальных случаев возобновления и переходов действуют
следующие условия повторного использования.

При возобновлении не останавливать процесс по старому PID: он мог быть
переиспользован; трактовка `running` и потерянного итога дана в
[интерпретации JSON](#интерпретация-json).
При новом head сохранить старые результаты с прежней версией и выбрать нужные
повторные проверки. Не объединять старый PASS с новой версией молча.
При том же head сверить относящиеся к задаче dirty-изменения, конфигурацию,
зависимости, тестовые данные и среду. Повторное использование допустимо только
при подтверждённой применимости сохранённого доказательства к итоговой версии
и нужному сценарию; перепроверять только затронутое или сомнительное.
