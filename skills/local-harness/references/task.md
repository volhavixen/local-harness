# Состояние задачи

Для долгой работы без S1–S7 сохранить краткое постоянное состояние: цель,
решения и их причины, изменения, проверки и следующий шаг — в имеющейся записи
или отдельном файле в `Work`. Длительность сама по себе не меняет классификацию;
необходимость run-каталога и этапов определяется матрицей.

Для нового существенного запуска скопировать [шаблон](../assets/task.md) в run-каталог,
заполнить по фактам. Не копировать туда всю историю чата. При смене стадии,
прерывании или принятии решения обновить: сделано, доказательства, следующий шаг.
Не хранить секреты/реальные env-файлы. Нужные версии инструментов фиксировать
в окружении задачи, а не навязывать другим проектам.

## Каталог запуска

Для существенной работы создать постоянный run-каталог вне репозитория, например
`~/Documents/Work/.harness/runs/<project>/<date>-<subject>-<short-sha>-<unique-suffix>/`.
До создания любых материалов применять
[правила размещения и realpath](../../../AGENTS.md#обязательное-размещение-проектов-без-выбранного-проекта).
Старые run-каталоги вне `Work` можно читать; без поручения не переносить.
Новые материалы писать в `Work` со ссылкой на прежние доказательства.
Служебный каталог skill в `~/.codex` не является местом материалов задачи.
Для небольшой правки действует исключение только из
[классификации](scope-and-applicability.md#1-когда-доработка-существенная).

## Определить режим

`develop`: исходный сценарий и дизайн → минимальное изменение → проверки → handoff.
`review`: точный head/base и требования → чтение diff → проверки в изолированной
копии → findings и готовая ручная приёмка. Исправление кода MR — отдельное действие
по поручению пользователя. Локальная подготовка среды уже входит в работу.

Сначала читать конфигурацию проверяемого коммита. Старый MR может не иметь новых
`AGENTS.md`, `env:check` или `check:quick`. Найти реальные составляющие проверок
в этой версии и записать выбранные команды. Не копировать package.json/CI/ESLint
из грязной основной копии. Если инструкции из основной копии задают правила,
применять их как guidance и явно отметить источник, не подменяя проверяемый код.

## Источники, решения и актуальные знания

До реализации или основного ревью установить источники ожидаемого поведения и
документы затронутых модулей. Различать актуальное принятое требование,
предложение/планируемое поведение, наблюдаемое поведение и историческое свидетельство. Код и тесты подтверждают
реализацию, но сами по себе не разрешают менять согласованный смысл требования.

В существующей записи источников отметить принятые внешние наборы, если они есть:
источник, точную версию, область применения и идентичность сохранённой копии — по
[правилам сторонних методик](../../../AGENTS.md#понимание-задач-и-эффективность-работы).

Для существенного решения сохранить выбор, причину, область применения,
ограничения и условие пересмотра. Использовать существующее состояние задачи и
документ, которому принадлежит решение; отдельный ADR нужен только при
практической пользе или требовании проекта. Неизвестные причины не выдумывать;
уточнять их до зависимого действия, если они могут изменить существенный выбор.

Определить, какие документы требуется сохранить без изменения, обновить, создать
или связать ссылками. Указать действия только для затронутых знаний, без пустых
документов и обязательной полной формы. Неизвестного владельца знания или конфликт
требований отметить явно; остановить только зависящие от этого решения действия.
Существующие пути документации и согласованные границы правок сохраняются;
параллельную базу знаний и новую структуру документации без поручения не создавать.

Если в проекте уже есть задача или план, использовать их для согласованного
объёма, проектного статуса и ссылок на актуальные решения. Локальное состояние
внешнего run-каталога хранит ход исполнения, среду и доказательства; ссылаться на
проектный план вместо второй расходящейся копии. Требование run-каталога для
существенной работы по S1–S7 сохраняется и без формальной проектной задачи.

Перед завершением проверить доступность необходимых для текущей работы системы
знаний из актуальной документации, включая причины решений и условия пересмотра.
Выполнить обновления в разрешённом объёме; если правки не разрешены, записать
конкретный пробел, документ/ответственного, если он известен, и следующий шаг.
Не объявлять обязательное обновление выполненным по наличию записи в run-каталоге;
неустранённый обязательный пробел ограничивает готовность соответствующей части.
Обязательные проверки и их состав эта процедура не меняет.

## Возобновить

1. Сверить каталог, head/base, режим и разрешённые действия с актуальным запросом.
2. Прочитать последнее состояние, `checks/*/result.json` и нужные логи.
   Сверить полноту плана и результатов по
   [матрице и критерию готовности](scope-and-applicability.md#3-применимость-отдельно-от-результата),
   включая отдельный обязательный набор проекта.
3. Интерпретировать сохранённые статусы и решать, какие доказательства можно
   использовать, по [правилам результатов](run-results.md#повторное-использование-и-утраченный-итог).
4. Продолжить первый незавершённый шаг. Пользователь не обязан заново объяснять
   известный контекст; сбой доступа/службы отделять от тестового падения.

## Улучшения harness

Конкретный урок сохранять в run-каталоге и разбирать по
[правилам исправлений пользователя](../../../AGENTS.md#понимание-задач-и-эффективность-работы).
Изменение инструкции и доказанное изменение поведения отражать отдельно.
Если расхождений нет, отдельный отчёт о самоанализе не нужен.
Новую автоматику добавлять только при повторяющемся затруднении.
Не менять общий CI и шаблон ради личной процедуры.
