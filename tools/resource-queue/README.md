# Общая очередь локальных проверок

Один тяжёлый слот на компьютер и до двух дополнительных лёгких/сетевых операций суммарно. Это явная очередь команд, а не перехват всех
процессов системы: проверка, запущенная напрямую в обход helper, не ограничивается.
Тяжёлые заявки получают слот в порядке регистрации (FIFO), включая screen-брони.
Лёгкие/сетевые заявки имеют отдельный FIFO допуска и общий предел 2.
Серверы и браузеры не останавливаются. Экземпляры до этапа1 не регистрировали заявки: их ожидания не видны и порядок
относительно зарегистрированных заявок не гарантируется. Уже работающие экземпляры
этапа1 сохраняют прежний протокол и записи; новые parallel-заявки ему совместимы.

Инструмент необязателен для базовой установки harness. Требуются Python 3.9+ и POSIX `fcntl`: macOS, Linux или WSL. Нативно в Windows эта очередь не запускается. Все согласованные участники должны использовать один экземпляр и одно состояние в одной среде; очередь WSL не перехватывает команды Windows.

Если очередь уже установлена, сохраните прежнее расположение helper и state. Обновление файлов отложите до свободного heavy-слота и завершения всех parallel-задач по `--status`, включая завершение screen-брони её владельцем. Не перемещайте активную очередь и не создавайте новую копию рядом: отдельный state разорвёт взаимное исключение.

После выбора единственного общего экземпляра задайте абсолютный путь (пример POSIX shell):

```sh
export HARNESS_QUEUE="/absolute/path/to/resource-queue/heavy_check.py"
```

Из нужной рабочей копии:

```sh
python3 "$HARNESS_QUEUE" --runner vitest -- pnpm exec vitest run
python3 "$HARNESS_QUEUE" -- pnpm lint
python3 "$HARNESS_QUEUE" -- pnpm typecheck
python3 "$HARNESS_QUEUE" --status
python3 "$HARNESS_QUEUE" --status --human
python3 "$HARNESS_QUEUE" --history --human --limit 10
```

## Классы нагрузки и параллельный допуск

Без нового флага поведение прежнее: `--class heavy`. Класс задаёт вызывающий агент
по фактической операции; имя команды не используется для автоматического облегчения.
Все классы используют тот же helper и тот же state, заявки/история общие.

| Класс | Когда применять | Допуск |
| --- | --- | --- |
| `heavy` | Полные lint/типы, полные unit/integration, сборки, мутации, OCR/ML, массовое хеширование, распаковка, браузер/компиляция; неопределённая нагрузка | Один прежний slot.lock |
| `light` | Проверка синтаксиса нескольких файлов, небольшой формат/валидатор, подтверждённо малый целевой unit без сборки, браузера и тяжёлых сервисов | До двух light/network суммарно, рядом с heavy |
| `network` | Конечный HTTP/API-запрос, опрос статуса, потоковая передача файлов без тяжёлой локальной обработки | Тот же общий предел двух light/network |

```sh
python3 "$HARNESS_QUEUE" --class light --label "syntax" --owner "task-id" -- python3 -m py_compile changed.py
python3 "$HARNESS_QUEUE" --class network --label "API status" --owner "task-id" -- curl --fail --max-time 30 https://example.com/status
```

Один worker для `light`/`network`; значение 2 отвергается. `network` не допускает
тестовые runners. Playwright и screen-бронь всегда `heavy`, включая автоматически
распознанный runner. Флаг не измеряет и не ограничивает фактическую RAM/CPU чужой
команды: полноценную сборку нельзя объявлять `light` ради обхода слота.

У heavy и parallel отдельные головы очереди. Каждый допуск выполняется под
коротким metadata.lock; сначала допускается голова своей очереди, при наличии
места следующий получает второй допуск. Это порядок допуска, а не порядок
первых побочных эффектов двух одновременно работающих процессов.
При заполненных двух местах новые light/network ждут их освобождения; heavy
при этом не ждёт их очереди. Длительные сетевые операции тоже занимают место.

Параллельные команды должны иметь независимые изменяемые данные и выходы:
отдельные временные каталоги/порты/результаты, где это требуется. Конфликтующие
операции изолируют либо обе выполняют как heavy. Один флаг класса не устраняет
гонки в общих файлах, БД и dev-сервере. Watch/daemon и бесконечный polling запрещены
для всех классов. Исходы и коды выхода сохраняются одинаково для всех классов.

Старые записи без `workload` считаются heavy. Новые parallel waiters используют
`phase=parallel_queued`: уже работающий helper этапа1 не примет их за голову
своей тяжёлой очереди. Старые процессы не перенастраиваются. Их старый status
не умеет показывать новые активные parallel-задачи; актуальный status показывает.
При откате сначала дождаться завершения всех parallel-задач и ожидающих заявок.

## Статус, заявки и история

Для понятного названия работы и владельца передавайте короткие метки:

```sh
python3 "$HARNESS_QUEUE" --label "project: unit tests" --owner "project-task" --runner vitest -- pnpm exec vitest run
```

Без `--label` используется только имя программы; аргументы команды и окружение
не сохраняются. Без `--owner` в JSON сохраняется `owner: null`, а human-вывод показывает `unspecified`. Не помещайте
секреты в метки. Метки ограничены 160 символами; управляющие символы удаляются.

`--status --human` показывает активную работу, проект, владельца, PID обёртки
и дочернего процесса, фазу, длительность работы и ожидающие заявки с позицией
и временем ожидания. Пока заявка ждёт, stderr сообщает её ID и раз в 30 секунд
позицию, время ожидания и известного владельца слота. FIFO считается от завершённой
регистрации; одновременные регистрации упорядочиваются короткой metadata-блокировкой.
Пустой список ожидающих не исключает участников версий до этапа1, не регистрирующих заявки.

`--status` сохраняет JSON-вывод и прежние поля `active`/`existing_checks`, добавляя
`waiting`, `parallel_active` и `limits`. `active` означает только владельца
тяжёлого слота и остаётся `null` при его свободе, даже если parallel-задачи работают.
У waiting есть общая позиция регистрации и lane/lane_position для своего допуска. Для старого владельца
неизвестные метки и времена не выдумываются: `legacy=true`, длительности `null`.
PID старой обёртки может уже отсутствовать, пока её ребёнок продолжает держать lock.

`--history` возвращает JSON с массивом `history`; `--human` включает читаемый вывод.
`--limit` задаёт число последних завершённых записей, от 1 до 1000, по умолчанию 20.
У каждой новой заявки сохраняются ID, порядковый номер, workload, метки, cwd, времена,
длительности, исход и код выхода. Времена JSON — секунды Unix; human-вывод использует
ISO 8601 с явным UTC. Ожидание измеряется монотонными часами от регистрации
до фактического запуска, включая `drain`; отдельно сохраняется время получения слота.
Длительность исполнения считается от запуска до наблюдаемого завершения.
Оставшееся время и ETA не предсказываются.

Исходы: `exited` (с реальным кодом), `launch_error` (127), `cancelled` (до запуска
или отменённая screen-бронь), `interrupted` (сигнал своей запущенной группе),
`released` (штатное освобождение screen-брони), `unknown` (завершение не наблюдалось).
Это исход команды, а не оценка покрытия тестами. Если wrapper убит, живой ребёнок
сохраняет slot и lease; после его завершения результат остаётся `unknown`, код —
`null`. При таком восстановлении `finished_at=null`, а `observed_finished_at`
фиксирует момент обнаружения; длительности помечены `timing_estimated=true`.
История начинается с новых заявок: старые ожидания задним числом не восстанавливаются.

Заявки хранятся в `state/requests/`, завершения — в `state/history/`; файлы создаются
с правами 0600, новые каталоги — 0700. Screen-токены не попадают в историю или human
статус; совместимый JSON активной брони по-прежнему содержит token для владельца.
Журнал хранится до явной отдельной очистки; `--limit` ограничивает вывод, не хранение.
Повреждённые метаданные останавливают запуск с ошибкой, не разрешая обход очереди.
Не удаляйте `metadata.lock`, `counter.json`, lease или файлы активных заявок вручную.

Старая версия helper может работать рядом с новой до естественного завершения.
Для отката дождитесь завершения всех новых заявок и броней, сохраните каталог
состояния и восстановите предыдущий helper, сохранив inode `slot.lock`.
Неизвестные новой схеме/повреждённые данные не исправляются автоматически.

Runtime, package manager и команды определяются проектом. По умолчанию один worker,
при свободных ресурсах допустим `--workers 2` перед `--`. Поддерживаются Vitest,
Jest, Playwright (если явно разрешён) и последовательный pytest без xdist.
Для generic-команды ограничение её внутренних процессов задаёт вызывающий агент:
запрещены параллельные агрегаторы и скрытые фоновые прогоны. Все реальные тестовые
флаги передаются процессу; queue не меняет конфиги проектов и CI.

С постоянным логом local-harness можно обернуть `check.py`; заранее задайте
`HARNESS_CHECK` в абсолютный путь установленного `scripts/check.py`:

```sh
python3 "$HARNESS_QUEUE" --label "unit tests" --owner "task-id" --runner vitest -- python3 "$HARNESS_CHECK" --run /absolute/run/outside/repository --name unit-1 --cwd /absolute/worktree -- pnpm exec vitest run
```

Очередь использует файловую блокировку `state/slot.lock`, автоматически освобождаемую
ядром. Никогда не удалять lock-файл: это создаёт второй независимый слот.
Файл `state/drain.json` содержит PID и время запуска проверок, уже работавших при
настройке. Новые команды ждут их естественного завершения; повторно использованный
PID и zombie не блокируют очередь. Уже работающие dev-серверы туда не входят.
Отмена ожидания не посылает сигнал владельцу. Если отменена собственная запущенная
команда, сигнал получает только её отдельная группа процессов. Если оболочка
аварийно завершилась, запущенная команда продолжает удерживать блокировку.
Команды должны быть конечными, без daemonize и фоновых потомков.

## Обход экранов и компиляция

Браузерные действия через CUA/Playwright-инструменты не являются дочерними
командами CLI. Для них перед навигацией нужно получить бронь **того же** слота:

```sh
python3 "$HARNESS_QUEUE" --reserve-screens manual-check --owner task-id
```

Оставить процесс работать в tool-session; если exec вернул session ID, продолжать
чтение его вывода до JSON `{"event":"screens_acquired","token":"..."}`.
Сообщение ожидания и наличие PID ещё не разрешают начинать браузерные действия.
Пока тяжёлые тесты идут, бронь ждёт; пока бронь удерживается, тяжёлые тесты и другие обходы ждут.
Независимые light/network разрешены рядом с бронью.

Получив token, выполнить конечный сценарий на уже работающем dev-сервере.
Дождаться загрузки/ответов и окончания вызванной компиляции по логам сервера;
при ошибке браузера тоже дождаться компиляции. После этого из другого tool-вызова:

```sh
python3 "$HARNESS_QUEUE" --release СВОЙ_TOKEN_ИЗ_JSON
```

Дождаться завершения процесса брони. Release использует уникальный token и не
посылает сигналов серверу, тестам или браузеру. Чужой/устаревший token отвергается.
Тяжёлые тесты нельзя ставить в очередь и ждать их внутри собственной брони: сначала release.
Не освобождать бронь в середине ещё продолжающейся компиляции. Нет автоматического
таймаута, который мог бы разрешить тесты во время неё; при забытом процессе владелец
проверяет `--status` и завершает свою бронь после окончания работы. Не удерживать
бронь на всё время жизни сервера/браузера или на время несвязанного анализа.

Автоматизированную **конечную** браузерную команду можно запускать обычным способом
через queue (для разрешённого Playwright — с `--runner playwright`), без второй брони.
Слоты не разрешают E2E сами по себе. Правила применяются к следующим сценариям:
текущие обходы, тесты и серверы не останавливать.

Протокол не перехватывает случайный reload, стороннего пользователя, автокомпиляцию
после несогласованного изменения исходников или прямые обходы очереди. Чаты должны
согласовывать такие действия и не менять исходники работающего проверяемого сервера
параллельно чужому тяжёлому прогону. Существующий server/watch не помещается в
вечный слот. Причина этого ограничения должна оставаться явной в отчётах.

Блокировка и параметры не становятся автоматически доступны в уже выполняющемся
контексте старого чата. Перед следующим запуском через очередь чат должен перечитать
актуальные принятые правила и пользоваться helper. Для новых чатов правило подключается
через постоянные инструкции фактической установки Codex (с учётом `CODEX_HOME`). Прямые запуски вне этого соглашения технически не перехватываются.

Проверки инструмента: `python3 -m unittest -v` в этой папке (лёгкие подпроцессы,
отдельные временные каталоги состояния). Не применять тестовый `--state-dir` для
рабочих проверок. Ничего не устанавливается и не добавляется в фоновые службы.

Ошибка сохранения PID после запуска не освобождает допуск преждевременно: helper
дожидается ребёнка и сохраняет известный исход, отмечая
`metadata_warning=child_pid_update_failed`, если итоговая история доступна для записи.
