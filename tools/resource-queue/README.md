# Общая очередь локальных проверок

Один занятый слот на компьютер. Это явная очередь команд, а не перехват всех
процессов системы: проверка, запущенная напрямую в обход helper, не ограничивается.
Порядок получения слота не гарантирует строгий FIFO. Серверы и браузеры не останавливаются.

Инструмент необязателен для базовой установки harness. Требуются Python 3.9+ и POSIX `fcntl`: macOS, Linux или WSL. Нативно в Windows эта очередь не запускается. Все согласованные участники должны использовать один экземпляр и одно состояние в одной среде; очередь WSL не перехватывает команды Windows.

Если очередь уже установлена, сохраните прежнее расположение helper и state. Обновление файлов отложите до свободного `--status`, включая завершение screen-брони её владельцем. Не перемещайте активную очередь и не создавайте новую копию рядом: отдельный state разорвёт взаимное исключение.

После выбора единственного общего экземпляра задайте абсолютный путь (пример POSIX shell):

```sh
export HARNESS_QUEUE="/absolute/path/to/resource-queue/heavy_check.py"
```

Из нужной рабочей копии:

```sh
python3 "$HARNESS_QUEUE" --runner vitest -- pnpm exec vitest run
python3 "$HARNESS_QUEUE" -- pnpm lint
python3 "$HARNESS_QUEUE" -- pnpm typecheck
python3 "$HARNESS_QUEUE" --status
```

Runtime, package manager и команды определяются проектом. По умолчанию один worker,
при свободных ресурсах допустим `--workers 2` перед `--`. Поддерживаются Vitest,
Jest, Playwright (если явно разрешён) и последовательный pytest без xdist.
Для generic-команды ограничение её внутренних процессов задаёт вызывающий агент:
запрещены параллельные агрегаторы и скрытые фоновые прогоны. Все реальные тестовые
флаги передаются процессу; queue не меняет конфиги проектов и CI.

С постоянным логом local-harness можно обернуть `check.py`:

```sh
python3 "$HARNESS_QUEUE" --runner vitest -- python3 ~/.codex/skills/local-harness/scripts/check.py --run /absolute/run/outside/repository --name unit-1 --cwd /absolute/worktree -- pnpm exec vitest run
```

Очередь использует файловую блокировку `state/slot.lock`, автоматически освобождаемую
ядром. Никогда не удалять lock-файл: это создаёт второй независимый слот.
Файл `state/drain.json` содержит PID и время запуска проверок, уже работавших при
настройке. Новые команды ждут их естественного завершения; повторно использованный
PID и zombie не блокируют очередь. Уже работающие dev-серверы туда не входят.
Отмена ожидания не посылает сигнал владельцу. Если отменена собственная запущенная
команда, сигнал получает только её отдельная группа процессов. Если оболочка
аварийно завершилась, запущенная команда продолжает удерживать блокировку.
Команды должны быть конечными, без daemonize и фоновых потомков.

## Обход экранов и компиляция

Браузерные действия через CUA/Playwright-инструменты не являются дочерними
командами CLI. Для них перед навигацией нужно получить бронь **того же** слота:

```sh
python3 "$HARNESS_QUEUE" --reserve-screens manual-check
```

Оставить процесс работать в tool-session; если exec вернул session ID, продолжать
чтение его вывода до JSON `{"event":"screens_acquired","token":"..."}`.
Сообщение ожидания и наличие PID ещё не разрешают начинать браузерные действия.
Пока тесты идут, бронь ждёт; пока бронь удерживается, тесты и другие обходы ждут.

Получив token, выполнить конечный сценарий на уже работающем dev-сервере.
Дождаться загрузки/ответов и окончания вызванной компиляции по логам сервера;
при ошибке браузера тоже дождаться компиляции. После этого из другого tool-вызова:

```sh
python3 "$HARNESS_QUEUE" --release СВОЙ_TOKEN_ИЗ_JSON
```

Дождаться завершения процесса брони. Release использует уникальный token и не
посылает сигналов серверу, тестам или браузеру. Чужой/устаревший token отвергается.
Тесты нельзя ставить в очередь и ждать их внутри собственной брони: сначала release.
Не освобождать бронь в середине ещё продолжающейся компиляции. Нет автоматического
таймаута, который мог бы разрешить тесты во время неё; при забытом процессе владелец
проверяет `--status` и завершает свою бронь после окончания работы. Не удерживать
бронь на всё время жизни сервера/браузера или на время несвязанного анализа.

Автоматизированную **конечную** браузерную команду можно запускать обычным способом
через queue (для разрешённого Playwright — с `--runner playwright`), без второй брони.
Слоты не разрешают E2E сами по себе. Правила применяются к следующим сценариям:
текущие обходы, тесты и серверы не останавливать.

Протокол не перехватывает случайный reload, стороннего пользователя, автокомпиляцию
после несогласованного изменения исходников или прямые обходы очереди. Чаты должны
согласовывать такие действия и не менять исходники работающего проверяемого сервера
параллельно чужому тяжёлому прогону. Существующий server/watch не помещается в
вечный слот. Причина этого ограничения должна оставаться явной в отчётах.

Блокировка и параметры не становятся автоматически доступны в уже выполняющемся
контексте старого чата. Перед следующим тяжёлым запуском чат должен перечитать
общие правила и пользоваться helper. Для новых чатов правило находится в
`~/.codex/AGENTS.md`. Прямые запуски вне этого соглашения технически не перехватываются.

Проверки инструмента: `python3 -m unittest -v` в этой папке (лёгкие подпроцессы,
отдельные временные каталоги состояния). Не применять тестовый `--state-dir` для
рабочих проверок. Ничего не устанавливается и не добавляется в фоновые службы.
